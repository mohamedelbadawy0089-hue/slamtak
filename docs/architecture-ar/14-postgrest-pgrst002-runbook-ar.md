# دليل تشغيل: إصلاح `PGRST002` (تعذّر بناء schema cache في PostgREST)

> **الجمهور:** مالك المشروع، من لوحة Supabase أو SQL Editor.
> **القاعدة الحاكمة:** كل خطوة هنا إمّا **قراءة** أو **إعدادات قابلة للرجوع** أو **إعادة تشغيل بلا فقدان بيانات**. لا حذف جداول، ولا استرجاع نسخ احتياطية، ولا مفاتيح `service_role` خارج خادم آمن.
> **الأدوات المرافقة:** `supabase/diagnostics/read-only-checks.sql` (الفحوص) و`scripts/supabase-health.mjs` (القياس الخارجي).

## 1. متى يُستخدم هذا الدليل

عندما يفشل التطبيق في قراءة أي جدول، أو يعطي فحص الصحة:

```bash
npm run check:supabase   # يخرج بالرمز 2 عند PGRST002
```

أو حين يرجع أي طلب `GET` على `/rest/v1/...`:

```json
{"code":"PGRST002","message":"Could not query the database for the schema cache. Retrying."}
```

الرسالة تعني: **PostgREST لا يستطيع تنفيذ استعلام الكتالوج الذي يبني به الكاش**، فيرفض كل قراءة وكتابة عبر Data API. التطبيق بريء من هذا العطل، وكذلك سياسات RLS — الخطأ يقع قبل تقييم أي سياسة.

## 2. تمييز الأعطال المتشابهة

| ما تراه | الرمز/الحالة | المعنى | أول إجراء |
|---|---|---|---|
| تعذّر بناء الكاش، والمصادقة تعمل | `PGRST002` / `503` | القاعدة على الأرجح حيّة، واستعلام الكاش فشل أو انتهت مهلته | هذا الدليل (يبدأ من §3) |
| مهلة مسبح اتصالات PostgREST | `PGRST003` / `504` | لا اتصال متاح لخدمة الطلب | القسم 2 من ملف الفحوص (الجلسات والاتصالات) |
| تعذّر الاتصال أصلًا | `PGRST000` / `PGRST001` / `503` | القاعدة لا تقبل اتصالات: استعادة، ترقية، أو توقف | اللوحة: Settings ← General، وحالة المشروع |
| المصادقة وData API ساقطان معًا | كل الطلبات تفشل | المشروع متوقف/مُعلَّق | Restore أو Resume من اللوحة |
| كل شيء يعطي `401 Invalid API key` | `401` | مفتاح خاطئ أو محجوب، لا عطل قاعدة | راجع `public/supabase-config.js` وبيئة النشر |
| قراءة تعطي `403` أو صفر صفوف | `403` / `[]` | الخدمة سليمة وRLS يعمل | ليس هذا الدليل؛ راجع العضوية في §7 |

## 3. القياس الخارجي أولًا (بلا كتابة)

شغّل الفحص من الطرفية؛ كل طلباته `GET/OPTIONS` ولا يطبع أي مفتاح:

```bash
npm run check:supabase
```

رموز الخروج: `0` سليم · `1` إعداد مفقود · `2` عطل PostgREST/`PGRST002` · `3` فشل المصادقة (وغالبًا المشروع متوقف) · `4` فشل شبكة.

مثال مقيس فعليًا في 2026-11-25 على المشروع `iksjhjxwphmvthryfeae`:

| المسار | النتيجة | دلالته |
|---|---|---|
| `/auth/v1/health` | `200` · GoTrue `v2.198.0` | المشروع يعمل، ليس متوقفًا |
| `/auth/v1/settings` | `200` | إعدادات المصادقة تُقرأ |
| `OPTIONS /rest/v1/rpc/two_step_verify` | `200` | بوابة PostgREST حيّة |
| `/storage/v1/...` | `400` (مسار غير صالح) | التخزين يستجيب |
| `GET /rest/v1/warehouses?select=id&limit=1` | `503 · PGRST002` · ~2.5s · `x-envoy-attempt-count: 6` | إعادة محاولة متكررة وفشل بناء الكاش |

هذا التوليف يستبعد «المشروع متوقف» ويحصر العطل في طبقة Data API. لاحظ الفرق: `PGRST002` يعني «وصلت إلى القاعدة لكن استعلام الكاش فشل»، أما `PGRST003` فيعني «لم أجد اتصالًا».

## 4. جمع الأدلة من اللوحة (قراءة فقط)

### 4.1 السجلات

Logs ← *Postgres* و*Edge/API*، وابحث عن:

- `canceling statement due to statement timeout` ⇒ مهلة استعلام الكاش.
- `too many connections` أو `remaining connection slots are reserved` ⇒ احتكار اتصالات.
- `deadlock detected` أو انتظار `Lock` طويل ⇒ قفل على الكتالوج.
- تكرار `PGRST002` في دفعات قصيرة ⇒ إعادة محاولة في حلقة، لا بطء واحد.

### 4.2 فحوص SQL

افتح SQL Editor (لا يمرّ على PostgREST، فيعمل رغم `503`) ونفّذ `supabase/diagnostics/read-only-checks.sql` **قسمًا قسمًا**، وسجّل الناتج:

| القسم | يفحص | النتيجة التي تشير إلى العطل |
|---|---|---|
| 1 | حياة القاعدة، `pg_is_in_recovery()` | `in_recovery = true` ⇒ انتظر الاستعادة، لا تصلح شيئًا |
| 2 | الجلسات و`idle in transaction` | تراكم جلسات قديمة ⇒ §5.3 |
| 3 | أدوار `authenticator`/`anon`/`authenticated` وصلاحيات المخطط | دور مفقود أو بلا `USAGE` ⇒ عطل إعداد، صعّد للمالك/الدعم |
| 4 | حجم كتالوج `public` | آلاف الكائنات ⇒ §5.2 |
| 5أ | views/matviews غير صالحة | أي صف ⇒ §5.4 |
| 5ب | قيود `NOT VALID` | أي صف ⇒ §5.4 |
| 6 | أقفال غير ممنوحة | أي صف ⇒ §5.4 |
| 7 | وجود جدول تتبّع الهجرات | `null` ⇒ ترحيل يدوي، وهو تفسير شائع لهجرات نصف مطبّقة |
| 8أ | إعداد `pgrst.*` الفعّال لأدوار القاعدة | `pgrst.db_schemas` يذكر اسمًا غير موجود ⇒ §5.1 |
| 8ب | الأسماء الموجودة فعلًا في القاعدة | قارنها بأسماء 8أ |

## 5. شجرة القرار: من الدليل إلى الإصلاح

نفّذ **الفرع الواحد** الذي تطابق أدلته، ثم اذهب إلى §7 للتحقق.

### 5.1 الأرجح: `db_schemas` يذكر schema محذوفًا

PostgREST يرفض بناء الكاش إذا أشار `pgrst.db_schemas` إلى مخطط غير موجود (شائع بعد حذف schema من القاعدة دون إزالته من Data API).

1. Project Settings ← **Data API** ← *Exposed schemas*: أزل الاسم غير الموجود في مخرجات 8ب، ثم **Save** (إعداد فقط، قابل للرجوع).
2. إن كان `ALTER ROLE authenticator SET pgrst.db_schemas` قد نُفِّذ يدويًا سابقًا، فاللوحة لا تدير القائمة؛ صحّحها دوريًا ثم أعد تحميل الإعداد:
   ```sql
   ALTER ROLE authenticator SET pgrst.db_schemas = 'public';
   NOTIFY pgrst, 'reload config';
   ```
   (وثّق القيمة القديمة قبل التغيير.)
3. إن كان الـschema مطلوبًا فعلًا وأُسقط بالخطأ، أعد إنشاءه فارغًا أولًا لتعود الخدمة، ثم أعِد كائناته بهجرة جديدة.

### 5.2 استعلام الكاش يتجاوز المهلة (كتالوج ضخم أو تضخّم)

الدليل: `statement timeout` في سجلات Postgres، أو أعداد ضخمة في القسم 4. الحل التدريجي: إعادة تحميل الكاش (§6)، ثم إعادة تشغيل المشروع (§6)، ثم معالجة التضخّم (تنظيف كائنات مهجورة، أو رفع مهلة الدور بعد مراجعة مالك). لا تغيّر `statement_timeout` قبل قراءة السجل.

### 5.3 احتكار اتصالات

الدليل: القسم 2 يُظهر `idle in transaction` كثيرة أو `total_sessions` قريبًا من الحد. أوقف العميل المتسبب (سكربت يعمل محليًا، دالة مجدولة، ORM بمسبح كبير). راجع Connection pooling في Database Settings، واضبط حجم المسبح بدل قتل الجلسات. إن لزم إنهاء جلسات خاملة قديمة فيكون ذلك بقرار صريح بعد مراجعة عمود `query`.

### 5.4 كائن غير صالح أو قفل على الكتالوج

الدليل: صفوف في 5أ/5ب/6. الإصلاح **بهجرة جديدة** في `supabase/migrations` (إنشاء/استبدال الـview، أو `ALTER TABLE ... VALIDATE CONSTRAINT`)، لا بأمر يدوي غير موثّق. إن كان السبب `ALTER TABLE` طويلًا يحمل قفلًا: انتظر انتهاءه أو أوقف الجلسة المالكة له بعد التأكد من هويتها.

### 5.5 كل شيء سليم في 1–8 والكاش ما زال معطوبًا

عملية PostgREST نفسها عالقة: اذهب إلى §6 (إعادة تشغيل المشروع). هذا لا يغيّر بيانات ولا مخططًا.

## 6. الإجراءات الآمنة (بالترتيب)

1. **إعادة تحميل الكاش** — SQL Editor، لا تغيّر بيانات ولا مخططًا:
   ```sql
   NOTIFY pgrst, 'reload schema';
   NOTIFY pgrst, 'reload config';
   ```
2. **إعادة تشغيل المشروع** — Project Settings ← General ← **Restart project**. توقف دقائق، بلا فقدان بيانات؛ تُعيد بناء الكاش من الصفر وتُخرج أي حالة عالقة.
3. بعد كل خطوة: `npm run check:supabase` والمطلوب `exit=0` (REST يعطي `200/401/403/404` بلا `PGRST002`).

## 7. التحقق من الإصلاح (وكذلك من جلب العضوية والدور)

### 7.1 الخدمة

 `npm run check:supabase` ⇒ `exit=0`، وسطر PostgREST بلا `PGRST002`.

### 7.2 الكود

 `npm run test:auth` ⇒ 17/17، ومنه اختبار «يجلب عضوية user_warehouses بالعميل الصحيح» الذي يثبت أن `verifySession` تستعلم `client.from('user_warehouses')` وتضع `tenant_id` و`warehouse_id` والدور في الجلسة، واختبار أن فشل الاستعلام لا يمنع الدخول.

### 7.3 الجلسة في المتصفح

بعد دخول ناجح وإكمال الخطوة الثانية:
```js
JSON.parse(localStorage.getItem('session'))
```
المتوقع: `tenant_id` غير فارغ، و`memberships` غير فارغة، و`role` هو الدور الحقيقي. **العلامة الحاسمة:** إن كان دورك في القاعدة `employee` وظهر `manager`، فالعضوية لم تُجلب — `manager` هو الافتراضي من `user_metadata`.

### 7.4 قراءة مباشرة بجلسة المستخدم

(مفتاح anon عام، وRLS يطبّق):
```js
const c = window.supabase.createClient(SUPABASE_URL, SUPABASE_ANON_KEY);
const { data: { session } } = await c.auth.getSession();
await c.from('user_warehouses')
  .select('tenant_id, warehouse_id, is_default, role:roles(name)')
  .eq('user_id', session.user.id)
  .order('created_at', { ascending: true })
  .limit(20);
```
يجب أن تُرجع صفوفًا (أو `[]` صريحًا لعدم وجود عضوية)، لا خطأ.

### 7.5 مطابقة القاعدة

في SQL Editor (قراءة فقط):
```sql
select uw.user_id, uw.tenant_id, uw.warehouse_id, uw.is_default, r.name as role
from public.user_warehouses uw
left join public.roles r on r.id = uw.role_id
order by uw.created_at;
```
قيم صف المستخدم هنا يجب أن تطابق ما في `localStorage.session`، وأن يظهر أثر `set_tenant_context` في `/purchases/invoices` ببيانات مخزنك لا شاشة فارغة.

## 8. ما لا يُفعل

- لا `service_role` في المتصفح ولا في سكربتات الفحص ولا في الوثائق.
- لا حذف أو إعادة إنشاء `public`، ولا DDL يدوي غير موثّق بهجرة.
- لا استرجاع نسخة احتياطية قبل تحديد السبب — يفقد بيانات أحدث بلا داعٍ.
- لا تغيير `statement_timeout` أو أحجام المسبح قبل قراءة سجلات القسم 4.
- لا تعطيل RLS ولا تغيير سياسة لعابر سبيل «لاختبار»؛ `PGRST002` لا علاقة له بالسياسات.

## 10. التصعيد

إذا بقي `PGRST002` بعد §5.١–§5.٥ و§6، ولم تُظهر الفحوص سببًا: صعّد إلى دعم Supabase مع `sb-request-id` من ترويسات الاستجابة، ومخرجات الأقسام 1–8، وتأكيد أن *Exposed schemas* يذكر `public` وحده وأن الإعداد الفعّال في 8أ مطابق له. لا تعِد إنشاء المشروع كحلٍّ أول — يفقد البيانات والروابط.
