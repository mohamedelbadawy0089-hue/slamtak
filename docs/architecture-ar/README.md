# دوسيه هندسة النظام — منصة إدارة مخازن الأدوية (المرحلة الأولى: الهندسة فقط)

> **حالة المرحلة:** تصميم مكتمل، **لم تُكتب أي برمجة ولم تُنشأ واجهات** في هذه المرحلة. التسليم ينتظر اعتماد المالك (Gate A) قبل أي سطر كود.
>
> **العلاقة بالوثائق الإنجليزية القائمة:** هذا الدوسيه هو **العرض العربي الرسمي والموحّد** لما هو موثّق بالإنجليزية في `docs/architecture/` (29 وثيقة + 26 ADR + 156 جدولًا فعليًا في قاعدة البيانات). لا يغيّر قرارًا معتمدًا إلا بإشارة صريحة تحت عنوان «قرار مطلوب»، ولا ينسخ الجداول الحالية، بل يعرّف **المخطط الهدف** ويبيّن الفجوات.

---

## 1. كيف تُقرأ هذه الوثائق

1. اقرأ هذا الملف كاملًا (فهرس + قرارات + مخاطر).
2. اقرأ `01` (المعمارية) ثم `02` (التقنيات) — هما أساس الاعتماد.
3. اقرأ `03` (العزل) و`04`+`05` (قاعدة البيانات) — أخطر أجزاء النظام.
4. الباقي مرجع تفصيلي يُراجَع بندًا بندًا مقابل «قائمة الاعتماد» في القسم 6.

## 3. الرؤية في عشرة أسطر

منصة SaaS متعددة المخازن لإدارة مخازن الأدوية في مصر: **حساب واحد = مخزن واحد**، لوحة تحكم مستقلة، **كتالوج أدوية مستقل تمامًا لكل مخزن**، مخزون قائم على التشغيلات (Batch/Lot) مع FEFO، ودفتر حركات غير قابل للحذف. تبدأ بمخزن واحد وتستوعب آلاف المخازن بلا إعادة بناء، لأن العزل مُنفَّذ في قاعدة البيانات (RLS + قيود) وليس في الواجهة، ولأن حدود الوحدات مرسومة منذ اليوم الأول بحيث يمكن استخراج أي وحدة كخدمة مستقلة لاحقًا دون تغيير العقود.

## 4. القرارات المعمارية الحاكمة (ملخص)

| القرار | الاختيار | لماذا في سطر |
|---|---|---|
| الشكل العام | **Modular Monolith** بوحدات حدودية + مبادئ DDD | أقصى بساطة تشغيلية اليوم، وأقصى قابلية فصل غدًا |
| تعدد المخازن | **Multi-Tenant SaaS بقاعدة ومخطط مشتركين + RLS** | أرخص وأسهل صيانة، وعزل مُثبت على مستوى القاعدة |
| حدود المستأجر | `tenant` ↔ `warehouse` بنسبة **1:1 مقيدة بقيد فريد** | يطابق قاعدة «حساب واحد = مخزن واحد» ويمنع الفروع الضمنية |
| الوصول للبيانات | **API فقط**؛ الواجهة لا ترى القاعدة ولا مفاتيحها | حد ثقة واحد، وإغلاق PostgREST |
| منطق الأعمال | في **طبقة الخدمات**؛ القاعدة للقيود والتكامل فقط | قابلية الاختبار والتتبع |
| الحقيقة المالية/المخزنية | **دفتر حركات append-only** + رصيد مشتق ومُتحقَّق | لا تعديل صامت، لا حذف تاريخي |
| التشغيلات | جدول `batches` مستقل + FEFO إلزامي في الصرف | متطلب دوائي وتنظيمي لا اختياري |
| Idempotency | مفتاح لكل عملية مالية/مخزنية + Outbox | يمنع الازدواج عند إعادة المحاولة |
| التشغيل | ملفان معتمدان: **Serverless صفري التكلفة** (افتراضي) و**Container** (بديل موثّق) | يحفظ قيد التكلفة بلا إغلاق باب التوسع |

## 8. ما لا يشمله هذا التسليم

- لا كود، لا واجهات، لا هجرات تنفيذية (مقصود).
- لا تطبيق جوال أصلي، لا ذكاء اصطناعي للتنبؤ بالطلب، لا ربط بالفاتورة الضريبية الإلكترونية — مصمَّمة كوحدات تُضاف لاحقًا.
- لا التزام بمزود SMS أو بوابة دفع (Adapter فقط).

## 9. اصطلاحات

- `MUST / MUST NOT` = إلزامي معماري، يُختبر آليًا.
- الجداول بالاسم الهدف بصيغة `snake_case` جمع، وكل جدول تشغيلي يحمل `tenant_id` **إلزاميًا** و`warehouse_id` عند الانتماء لمخزن.
- كل مبلغ `numeric(14,2)`، كل كمية `numeric(14,3)`، كل معرّف `uuid` (v7 للجداول عالية الكتابة)، وكل وقت `timestamptz`.
