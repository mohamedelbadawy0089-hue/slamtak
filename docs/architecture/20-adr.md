## ADR-001 — Modular Monolith بدل Microservices

**السياق:** فريق 5–6 مطورين، منتج واحد، مخزن واحد في البداية، وحاجة لتسليم سريع بتكلفة منخفضة. خدمات مصغّرة تعني شبكة، تتبع موزع، نشر متعدد، واتساق نهائي معقد.

**القرار:** تطبيق NestJS واحد مقسّم إلى وحدات (contexts) بحدود معلنة، تُفرض آليًا بـ `dependency-cruiser`.

**البدائل:** (أ) Microservices من البداية — مرفوض: تكلفة تشغيل ومعرفية. (ب) تطبيق Express بلا بنية — مرفوض: انهيار الحدود. (ج) Serverless functions — مرفوض: معاملات ومهام طويلة.

**النتائج:** (+) سرعة، معاملات محلية، تتبع بسيط، تكلفة أقل. (−) خطر التشابك، وحاجة انضباط مراجعة. (–) نشر كلي حتى عند تغيير وحدة واحدة.

**التكلفة:** وقت انضباط الحدود (ساعات/PR) مقابل توفير ~40% من تعقيد التشغيل.
**المخاطر:** تشابك تدريجي → تخفيف: فحص آلي + مراجعة معمارية شهرية + إشارات فصل واضحة (→ `17` §3).
**المراجعة:** عند فريق > 12 مطورًا أو حاجة نشر مستقل لوحدة.

## ADR-002 — قاعدة مشتركة + RLS بدل قاعدة لكل عميل

**السياق:** تحول من مخزن واحد إلى آلاف المخازن. الخيارات: قاعدة لكل عميل (تكلفة/تشغيل)، مخطط لكل عميل (تعقيد الهجرات)، أو قاعدة مشتركة بعزل منطقي.

**القرار:** قاعدة واحدة، مخطط `public`، `tenant_id` + RLS `FORCE` + مفاتيح مركبة. العزل الفيزيائي خيار تعاقدي لاحق.

**البدائل:** DB-per-tenant (+3x تكلفة، هجرات ×N)، Schema-per-tenant (هجرات معقدة، أدوات تصطدم بالـ schema)، NoSQL (فقدان RLS والقيود).

**النتائج:** (+) تكلفة أقل، هجرة واحدة، تحسينات مشتركة. (−) خطر "خطأ واحد يصيب الجميع" → تُخففه RLS والاختبارات. (–) جار مزعج → حدود لكل Tenant. (–) استعلام عابر للمخازن ممنوع بالتصميم (وهذا مطلوب).

**التكلفة:** ~$25–60/شهر للقاعدة المشتركة مقابل مئات لو انفصلت.
**المخاطر:** ثغرة عزل = أثر جماعي → تخفيف: A1–A27 في CI + منع النشر عند الفشل.
**المراجعة:** عند طلب مؤسسي بعزل تعاقدي أو متطلب إقامة بيانات.

## ADR-003 — فصل `tenant` / `branch` / `warehouse`

> **مُستبدَل جزئيًا بـ ADR-025** (2026-11-08): بقي فصل الحساب عن الموقع الفيزيائي، وأُلغي مستوى الفرع، وصار المخزن **1:1** مع الحساب. وكلفة «سكربت الترحيل» أدناه لم تعد قائمة: **لا ترحيل بيانات** (ADR-026). يُقرأ هذا القرار كتاريخ قرار لا كإرشاد تنفيذي.

**السياق:** النظام الحالي يستخدم `warehouse_id` كحدّ عزل واحد، ما يخلط بين الحساب التجاري والفرع والموقع الفيزيائي. هذا يمنع فروعًا متعددة ويفسد التقارير المجمّعة على مستوى الحساب.

**القرار:** `tenants` (الحساب) → `branches` (النطاق التشغيلي) → `warehouses` (الموقع الفيزيائي) → `storage_locations`. الصلاحيات تُنطَّق على الفرع/المخزن، والعزل على الـ Tenant.

**البدائل:** الإبقاء على `warehouse_id` كـ Tenant — مرفوض: يقيّد النمو. إضافة `branch_id` فقط بلا Tenant — مرفوض: لا عزل حقيقي.

**النتائج:** (+) دعم فروع ومخازن متعددة، تقارير على مستوى الحساب، تسعير/صلاحيات دقيقة. (−) ترحيل بيانات أعقد، وزيادة عدد الجداول. (–) كل استعلام يحتاج تمييز النطاق الصحيح.

**التكلفة:** ~2 أسابيع إضافية في Phase 1 + سكربت ترحيل.
**المخاطر:** ترحيل خاطئ يخلط بيانات فرعين → تخفيف: مطابقة عددية قبل/بعد + إعادة تشغيل آمنة.
**المراجعة:** لا تُراجع؛ قرار بنيوي.

## ADR-004 — الوصول للبيانات عبر API فقط وإغلاق PostgREST

**السياق:** الواجهة الحالية تتصل بـ Supabase PostgREST بمفتاح anon، والـ RLS هي خط الدفاع الوحيد. المنطق التجاري مبعثر بين المتصفح والقاعدة، ولا توجد طبقة تفرض قواعد (تسعير، ائتمان، موافقات).

**القرار:** NestJS هو المسار الوحيد. PostgREST يُغلق أمام العامة (أو يُقيَّد بشبكة داخلية). مفاتيح الخدمة لا تُرسل للمتصفح أبدًا.

**البدائل:** (أ) الإبقاء على PostgREST مع RLS فقط — مرفوض: لا يمنع تلاعب الأسعار، ولا يوفّر تدقيقًا موحدًا. (ب) استخدام RPC لكل عملية — مرفوض: يكرّر منطقًا في SQL ويصعّب الاختبار. (ج) GraphQL مباشر للقاعدة — مرفوض: سطح هجوم أوسع.

**النتائج:** (+) حد ثقة واحد، عقود واضحة، تدقيق وتدوير مركزي. (−) طبقة إضافية (زمن ~5–15ms)، وجهد بناء أولي.

**التكلفة:** ~4 أسابيع في Phase 1 لتأسيس الـ API.
**المخاطر:** بقاء مسارات قديمة مفتوحة → تخفيف: جرد مسارات + اختبار A6 في CI.
**المراجعة:** عند الحاجة لتكامل قراءة عالي الأداء (نسخة قراءة مخصصة، لا فتح كتابة).

## ADR-005 — مصادقة ذاتية بدل Supabase Auth

**السياق:** Supabase Auth (GoTrue) لا يوفّر بسهولة: تحققًا ثانيًا مخصصًا لكل مخزن، ربط جهاز، سياسات كلمة مرور، إبطالًا جماعيًا فوريًا، وتحكمًا كاملًا في Claims. كما أن تجزئات كلمات المرور غير قابلة للتصدير.

**القرار:** مصادقة داخل NestJS: Argon2id، JWT ES256 قصير، Refresh متداول باكتشاف إعادة الاستخدام، جلسات في القاعدة، MFA (TOTP).

**البدائل:** (أ) البقاء على GoTrue — مرفوض: قيود على سياسات التحقق والإبطال. (ب) Auth0/Clerk — مرفوض: تكلفة لكل مستخدم واعتماد خارجي وقيود توطين. (ج) Keycloak — مرفوض: عبء تشغيل كبير.

**النتائج:** (+) تحكم كامل، بلا تكلفة لكل مستخدم، تكامل مع الأدوار. (−) مسؤولية أمنية كاملة علينا (وهي موجودة أصلًا). (–) ترحيل مستخدمين يحتاج مسارًا مزدوجًا — **غير مطلوب الآن:** لا ترحيل (ADR-026).

**التكلفة:** ~2 أسابيع + مراجعة أمنية.
**المخاطر:** خطأ في التطبيق (تدوير/إبطال) → تخفيف: اختبارات مصادقة شاملة + مراجعة خارجية قبل الإنتاج.
**المراجعة:** سنويًا أو عند حاجة SSO للمؤسسات.

## ADR-006 — PostgreSQL مُدار كمزوّد قاعدة فقط

**السياق:** نحتاج PITR ونسخًا احتياطيًا وترقيات أقل عبئًا، بلا تبنّي كامل لمنصة BaaS (التي تتعارض مع ADR-004).

**القرار:** Supabase Pro أو Neon كـ PostgreSQL مُدار فقط. لا نستخدم PostgREST ولا Auth ولا Realtime الخاصة بهم. Storage: R2/S3 عبر S3 API.

**البدائل:** RDS (أغلى ~3x)، تشغيل PostgreSQL على VPS (مسؤولية نسخ وترقيات)، Aurora Serverless (تكلفة غير متوقعة).

**النتائج:** (+) PITR جاهز، تكلفة منخفضة، SQL قياسي. (−) اعتماد على مزوّد (يُخففه SQL القياسي وإمكانية `pg_dump`). (–) حدود اتصالات تحتاج Pooler.

**التكلفة:** $25–60/شهر.
**المخاطر:** تغيّر تسعير/سياسة مزوّد → تخفيف: بلا ميزات حصرية، خطة نقل موثقة.
**المراجعة:** سنويًا.

## ADR-007 — Drizzle ORM بدل Prisma/TypeORM

**السياق:** نحتاج تحكمًا صريحًا في SQL والمعاملات لتنفيذ `SET LOCAL` وسياسات RLS وقفل الصفوف وأقسام الجداول.

**القرار:** Drizzle ORM + `pg` Pool، مع استعلامات SQL صريحة عند الحاجة.

**البدائل:** Prisma (طبقة إضافية، محرك ثنائي، تحكم أقل في الجلسة/المعاملة)، TypeORM (صيانة أضعف، سلوك غير متوقع)، SQL خام بالكامل (بلا أنواع).

**النتائج:** (+) SQL مقروء، أنواع دقيقة، بلا محرك منفصل، وقت إقلاع أقل. (−) نظام بيئي أصغر، وأدوات إدارة أقل. (–) فريق يحتاج معرفة SQL.

**التكلفة:** منحنى تعلم ~أسبوع.
**المخاطر:** تغييرات API في إصدارات 0.x → تخفيف: تثبيت دقيق + اختبار ترقية في staging.
**المراجعة:** عند استقرار 1.0 أو حاجة ميزات إدارة متقدمة.

## ADR-008 — أصل عام واحد

**السياق:** فصل الواجهة عن API على نطاقات مختلفة يفرض CORS، وكوكيز `SameSite=None`، وتخفيف CSRF أعقد، ومشاكل تسريب Referer؛ ويضاعف احتمالات الخطأ الأمني.

**القرار:** `app.slamtak.com` يخدم الواجهة، و`/api/*` يُوجَّه داخليًا للـ API عبر Caddy. الكوكيز `HttpOnly; Secure; SameSite=Lax; Path=/`.

**البدائل:** `api.` منفصل مع Bearer tokens في الذاكرة — مرفوض: عرضة لـ XSS. نطاقان مع CORS + SameSite=None — مرفوض: تعقيد وحماية أضعف.

**النتائج:** (+) لا CORS، CSRF أبسط، أداء أفضل (HTTP/2 واحد). (−) الـ API ليس مستقلًا للنطاق (لا يحتاجه الموبايل: يستخدم Bearer). (–) توجيه الحافة يجب أن يكون دقيقًا.

**التكلفة:** لا شيء.
**المخاطر:** خطأ في قواعد التوجيه يخلط الأصول بالـ API → تخفيف: اختبارات توجيه + Smoke بعد كل نشر.
**المراجعة:** عند إتاحة API عامة لشركاء (نطاق منفصل مخصص للشركاء).

## ADR-009 — `SET LOCAL` مع مجمّع اتصالات في وضع المعاملة

**السياق:** RLS تعتمد على متغير جلسة، والـ Pooler يعيد استخدام الاتصالات. `SET` الدائم يتسرب بين الطلبات ويسبب أخطر خلل عزل ممكن.

**القرار:** `set_config('app.tenant_id', $1, true)` داخل كل معاملة، وممنوع `SET` غير محلي، وممنوع `pg_advisory_lock` غير `_xact_`، وكل كتابة داخل معاملة.

**البدائل:** جلسة مخصصة لكل طلب (Session mode) — مرفوض: يحدّ التوسع بشدة. اتصال مباشر بلا Pooler — مرفوض: انفجار اتصالات. الاعتماد على RLS بلا سياق — مرفوض: لا يعمل.

**النتائج:** (+) أمان مع كفاءة Pooler. (−) كل عملية تحتاج معاملة (وهو مطلوب أصلًا للذرية). (–) أي استعلام خارج معاملة يفشل → يظهر مبكرًا في الاختبار.

**التكلفة:** لا شيء.
**المخاطر:** نسيان `SET LOCAL` في Repository جديد → تخفيف: `withTenantTx` الوحيدة المسموحة + اختبار يفتح 50 معاملة متوازية بمخزنين.
**المراجعة:** لا تُراجع.

## ADR-010 — منطق الأعمال في الخدمات، والقاعدة للقيود فقط

**السياق:** النظام الحالي يضع جزءًا كبيرًا من المنطق في Triggers ودوال PL/pgSQL. هذا يعطي ذرية قوية لكنه يجعل السلوك غير مرئي في الكود، صعب الاختبار، وصعب التتبع عند التغيير.

**القرار:** المنطق في خدمات التطبيق. القاعدة تحتفظ بـ: القيود، RLS، Triggers حماية (منع تغيير `tenant_id`، تحديث الرصيد من الحركة، منع تعديل معتمد)، ودوال الاتساق. لا سير عمل (workflow) في Triggers.

**البدائل:** كل المنطق في القاعدة — مرفوض: يقيّد التطور ويصعّب الاختبار. كل المنطق في الكود بلا قيود — مرفوض: يسمح بفساد بيانات.

**النتائج:** (+) سلوك مرئي ومختبَر، تتبع أفضل. (−) بعض العمليات تحتاج معاملة أطول قليلًا. (–) خطر نسيان قيد في الكود → تُغطى بقيود القاعدة الحرجة.

**التكلفة:** ترحيل منطق Triggers تدريجيًا (~3 أسابيع موزعة).
**المخاطر:** اختلاف سلوك بين القديم والجديد → تخفيف: اختبارات مقارنة قبل/بعد لكل Trigger مُرحَّل.
**المراجعة:** عند ظهور حالة تحتاج ذرية لا يمكن ضمانها في طبقة الخدمة.

## ADR-011 — Idempotency + Outbox لكل عملية مالية

**السياق:** إعادة المحاولة (شبكة/مستخدم/عامل) تُنشئ فواتير مزدوجة أو حركات مزدوجة. واستدعاء الخدمات الخارجية داخل المعاملة يسبب معاملات طويلة وفشلًا جزئيًا.

**القرار:** كل POST مالي/مخزني يقبل `Idempotency-Key` بقيد فريد. وكل حدث يُكتب في `outbox_events` داخل نفس المعاملة ثم يُنشر لاحقًا.

**البدائل:** بلا Idempotency — مرفوض: أخطاء مالية مؤكدة. نشر مباشر للأحداث — مرفوض: فقدان/تكرار. Saga خارجية — مرفوض: تعقيد غير مبرر الآن.

**النتائج:** (+) بلا ازدواج، بلا فقد أحداث، معاملات قصيرة. (−) جدول إضافي ومهمة نشر. (–) مستهلكون يجب أن يكونوا Idempotent.

**التكلفة:** ~1 أسبوع تأسيس.
**المخاطر:** تراكم Outbox عند تعطل العامل → تخفيف: تنبيه على العمق + إعادة محاولة + Dead letter.
**المراجعة:** عند إدخال وسيط رسائل خارجي.

## ADR-012 — دفتر حركات للمخزون

**السياق:** تعديل الرصيد مباشرة يفقد التفسير ويجعل الجرد والمراجعة مستحيلين، ويعرّض النظام لخسائر غير مكتشفة.

**القرار:** `stock_movements` append-only، والرصيد في `stock_batches` إسقاط يتحدث بنفس المعاملة. لا `UPDATE` مباشر على الرصيد من التطبيق.

**البدائل:** رصيد فقط بلا دفتر — مرفوض: لا تتبع. Event Sourcing كامل — مرفوض: تعقيد أعلى من الحاجة.

**النتائج:** (+) تفسير كل رقم، مراجعة خارجية، تقارير موثوقة. (−) حجم بيانات أكبر (يُعالج بالتقسيم). (–) إعادة الحساب عند التصحيح تحتاج حركة عكسية.

**التكلفة:** مساحة تخزين إضافية ~20%، وتقسيم شهري مطلوب.
**المخاطر:** اختلاف بين الدفتر والرصيد → تخفيف: مهمة تحقق ليلية + `verify_ledger_consistency`.
**المراجعة:** لا تُراجع.

## ADR-013 — UUID + مفاتيح مركبة مع `tenant_id`

**السياق:** المعرّفات المتتابعة تسمح بالتعداد وتكشف الحجم. والمفاتيح المفردة تسمح — نظريًا — بربط سجل بمخزن آخر إن أخطأ الكود.

**القرار:** `uuid` للمفاتيح، و`PRIMARY KEY (tenant_id, id)`، وكل FK مركّب مع `tenant_id`.

**البدائل:** `bigserial` (قابل للتعداد)، ULID (مقبول لكن بلا ميزة هنا)، مفاتيح مفردة (لا يمنع الخلط بنيويًا).

**النتائج:** (+) منع بنيوي للخلط، بلا تعداد. (−) فهارس أكبر قليلًا، وأرقام مستندات منفصلة (نستخدم `document_sequences` للعرض). (–) استعلامات أطول كتابةً.

**التكلفة:** ~10–15% حجم فهارس إضافي.
**المخاطر:** أداء إدراج لـ UUIDv4 عشوائي → تخفيف: مراقبة، واستخدام `gen_random_uuid` مع أقسام وجداول مناسبة.
**المراجعة:** عند بلوغ جداول ضخمة يمكن تقييم UUIDv7.

## ADR-015 — Redis + BullMQ للمهام غير المتزامنة

> **مُستبدَل بـ ADR-020** (2026-11-06): لا Redis مجاني يتحمّل استقصاء الطوابير؛ استُبدل بـ pg-boss على PostgreSQL نفسه.

**السياق:** تقارير وتصدير PDF ومزامنة ETA وإشعارات لا يجوز أن تعطّل الطلبات أو تُنفَّذ داخل معاملة.

**القرار:** Redis (كاش، حدود معدل، Pub/Sub) + BullMQ (طوابير، إعادة محاولة، مجدولات).

**البدائل:** تنفيذ متزامن — مرفوض: زمن استجابة ومخاطر فشل. RabbitMQ — مرفوض: عبء تشغيل إضافي بلا حاجة. SQS — مرفوض: تكلفة واعتماد سحابي مبكر. `pg_cron` فقط — مرفوض: بلا إعادة محاولة/مراقبة كافية.

**النتائج:** (+) مهام موثوقة، فصل أحمال، جدولة. (−) مكوّن إضافي قد يفقد البيانات المؤقتة. (–) الحاجة لمراقبة طول الطوابير.

**التكلفة:** $0–15/شهر.
**المخاطر:** فقد Redis يفقد طوابير غير منشورة → تخفيف: AOF + Outbox كمصدر للحقيقة + إعادة إنشاء المهام.
**المراجعة:** عند > 5k مهمة/دقيقة أو حاجة ترتيب صارم بين خدمات.

## ADR-018 — VPS + Docker Compose أولًا، Kubernetes لاحقًا

> **مُستبدَل بـ ADR-021** (2026-11-06): قيد التكلفة الصفرية ألغى VPS المدفوع. يُقرأ هذا القرار كتاريخ قرار لا كإرشاد تنفيذي.

**السياق:** نحتاج نشرًا موثوقًا بتكلفة منخفضة وتحكمًا كاملًا، بلا فريق DevOps متفرغ.

**القرار:** VPS واحد (قابل للترقية) + Docker Compose + Caddy + Cloudflare. كل خدمة صورة مستقلة تصفِح الإعدادات من البيئة، لتسهيل الانتقال لاحقًا.

**البدائل:** Kubernetes من البداية — مرفوض: تعقيد لا يقابله حجم. منصة PaaS (Render/Railway) — مرفوض: تكلفة 2–3x وحدود. Serverless — مرفوض: مهام طويلة ومعاملات.

**النتائج:** (+) تكلفة منخفضة، تحكم كامل، بساطة. (−) مسؤولية النسخ والمراقبة علينا. (–) التوسع الأفقي يدوي (Compose + نسخ).

**التكلفة:** $15–45/شهر.
**المخاطر:** نقطة فشل واحدة → تخفيف: نسخ احتياطي PITR + صورة قابلة لإعادة النشر في ≤ 15 دقيقة + خطة نقل موثقة.
**المراجعة:** عند > 30 حاوية أو حاجة توزيع جغرافي أو فريق DevOps متفرغ.

## ADR-019 — التكلفة الصفرية كقيد معماري أول

**السياق:** قرار المالك (2026-11-06): التكلفة في التطوير والتجربة والتشغيل الأولي = صفر، بلا بطاقة بنكية وبلا فوترة تلقائية، بلا مساس بأمان البيانات.

**القرار:** يصبح «صفر تكلفة» قيدًا مُلزمًا يُقاس عليه كل قرار تقني، بأولوية أعلى من الراحة التشغيلية وأقل من الأمان وسلامة الأرصدة. كل خدمة تُعتمد فقط بعد تسجيل اسمها ورابطها وحدودها وبديلها المجاني (`27` §2)، وكل مورد قريب من حده يُعالج بالأرشفة أو التقييد قبل بلوغه. لا ترقية مدفوعة تلقائية، ولا مفتاح API مدفوع.

**البدائل:** (أ) خطة مدفوعة مبكرة 60–120$/شهر — مرفوضة: نفقة قبل إيراد. (ب) استضافة ذاتية على جهاز المالك — مرفوضة: توفّر وسلامة بيانات أسوأ. (ج) مجاني بلا سقف مكتوب — مرفوضة: تتحول إلى توقف مفاجئ.

**النتائج:** (+) لا نفقة ولا مخاطرة فوترة. (+) كل قيد موثّق بنقطة تنبيه. (−) RPO يتراجع إلى 24 ساعة، ونوم/إيقاف تلقائي يجب منعه بمهام مراقبة، وسقف 500 MB يفرض أرشفة.

**التكلفة:** صفر نقدًا؛ التكلفة الحقيقية وقت هندسي في الأرشفة والمراقبة.
**المخاطر:** الوصول إلى حد مجاني بلا تنبيه → تخفيف: `27` §8 يفرض تنبيهًا عند 70% لكل مورد.
**المراجعة:** عند أول عميل يدفع أو تجاوز 70% من أي حد.

## ADR-020 — pg-boss بدل Redis + BullMQ

> **مُستبدَل جزئيًا بـ ADR-023** (2026-11-06): لا عملية طويلة العمر في Edge Functions، فانتقل تنفيذ المهام إلى `pg_cron` + `pg_net`. يبقى صحيحًا أن Redis لا يُستخدم.

**السياق:** الطوابير مطلوبة (تقارير، إشعارات، مزامنة، PDF). BullMQ يحتاج Redis مستمر الاستقصاء، وأي Redis مُدار مجاني له حدود أوامر شهرية ضيقة تُستهلك حتى بلا عمل حقيقي.

**القرار:** pg-boss على PostgreSQL نفسه، في مخطط `app`, مع نفس ضمانات «مهمة واحدة تُنفَّذ مرة واحدة» عبر `FOR UPDATE SKIP LOCKED`، وربط كل مهمة بـ `tenant_id`.

**البدائل:** BullMQ + Upstash Free (حد أوامر غير كافٍ)، Graphile Worker (مكافئ لكن pg-boss أبسط في الجدولة)، جدولة داخل تطبيق الـ API بلا طابور (تفقد المهام عند إعادة التشغيل).

**النتائج:** (+) خدمة أقل، صفر تكلفة، اتساق المهمة مع معاملة العمل. (−) ضغط إضافي على القاعدة المشتركة (500 MB / CPU مشترك). (–) لا عزل موارد بين الطوابير.

**التكلفة:** صفر.
**المخاطر:** طابور يستهلك CPU القاعدة → تخفيف: مهام ثقيلة تُنفَّذ خارج ساعات الذروة، ومؤشر حجم الطابور في لوحة المراقبة.
**المراجعة:** عند تجاوز 50k مهمة/يوم أو حاجة عزل موارد.

## ADR-021 — استضافة مجانية، وقبول RPO = 24 ساعة

> **الحالة:** معتمد — المسار (ب): Oracle Cloud أساسي + Google احتياطي، ببطاقة تحقق فقط (2026-11-06). التفاصيل والمخاطر في [`27`](27-free-tier-architecture.md) §10.1.

**السياق:** لا يوجد مزوّد تشغيل مجاني بلا قيود: Render Free يعلن صراحة أنه غير مخصص للإنتاج، وVercel Hobby يمنع الاستخدام التجاري، وCloudflare Workers محدود بـ10ms CPU لا تكفي Argon2id.

**القرار:** مساران معلنان. **أ — تجربة بالكامل بلا بطاقة:** Next.js على Cloudflare Pages + NestJS على Render Free + Supabase Free + R2، مع مهمة إبقاء يقظة كل 10 دقائق ومنع إيقاف القاعدة يوميًا. **ب — إنتاج مجاني ببطاقة تحقق فقط:** نفس الكود على Oracle Cloud Always Free (أو Google e2-micro) مع Docker Compose. في المسارين: نسخ احتياطي `pg_dump` يومي مشفّر إلى R2، و**RPO = 24 ساعة** معلن في `26` §1 بدل 5 دقائق.

**البدائل:** Vercel Hobby (مخالف للشروط التجارية)، Render Free كإنتاج دائم (مخالف لتوصية المزوّد)، Cloudflare Workers + Hono (يتطلب إعادة كتابة API ويفقد Argon2id الأصلي).

**النتائج:** (+) صفر تكلفة، قابلية نقل كاملة (Docker + SQL + R2). (−) زمن استيقاظ ~دقيقة في المسار أ، ونافذة فقدان بيانات 24 ساعة في المسارين، ومسؤولية النسخ علينا.

**التكلفة:** صفر نقدًا.
**المخاطر:** إيقاف مشروع Supabase بعد خمول أو نفاد ساعات Render → تخفيف: مهام مراقبة + UptimeRobot + Runbook «أول 15 دقيقة» في `26` §5.
**المراجعة:** قبل أول مخزن حقيقي (اختيار المسار), وعند أول عميل يدفع.

## ADR-022 — Supabase Edge Functions بوابة الـ API الوحيدة

**السياق:** اختار المالك (2026-11-06) ثلاثية: Cloudflare Pages للواجهة، Supabase لقاعدة البيانات وRLS، وEdge Functions لكل المنطق البرمجي. القرار السابق كان NestJS في حاوية على خادم.

**القرار:** كل طلب HTTP يدخل عبر Edge Functions. الاتصال بالقاعدة عبر **Supavisor (وضع المعاملات، المنفذ 6543)** بدور `slamtak_app` وبكلمة مرور خاصة، ثم `BEGIN` → `set_config('app.tenant_id', …, true)` و`set_config('app.user_id', …, true)` → استعلامات → `COMMIT`. لا `service_role` لأي بيانات مخزن. PostgREST يبقى مغلقًا: المتصفح لا يتحدث إلى القاعدة أبدًا.

**لماذا لا يكسر العزل:** سياسات RLS الـ47 لا تعرف من يتصل؛ تعرف `app.current_tenant()` فقط. ما دام الاتصال بدور محدود وبـGUC مضبوط داخل المعاملة، فالعزل كما هو حرفيًا. الخطر الوحيد هو `service_role` — ولذلك يُمنع في مسار بيانات المخازن بحد صارم.

**البدائل:** NestJS على Oracle (ADR-021، بطاقة + صيانة نظام)؛ PostgREST مباشرة من المتصفح (يفقد تحقق الخادم وحدود المعدل والسياق)؛ Cloudflare Workers (10ms CPU لا تكفي Argon2id).

**النتائج:** (+) لا خادم دائم ولا بطاقة ولا صيانة نظام. (+) قرب من القاعدة = زمن استجابة أقل. (−) حد **2 ثانية CPU** لكل طلب، وإقلاع بارد 100–400ms، وارتباط بـDeno/Supabase.

**التكلفة:** صفر ضمن 500,000 استدعاء/شهر.
**المخاطر:** تجاوز ميزانية CPU في تقارير ثقيلة → تقسيم إلى دفعات (`28` §7). قفل المزوّد → منطق الأعمال في حزم TS عادية، والـDeno محوّل رفيع فقط.
**المراجعة:** عند 70% من الاستدعاءات أو أول طلب يتجاوز 1.5 ثانية CPU.

## ADR-023 — pg_cron + pg_net بدل عامل طوابير دائم

**السياق:** ADR-020 اختار pg-boss، وهو يحتاج عملية Node طويلة العمر تستقصي الجدول. Edge Functions تعيش لعمر الطلب فقط، فلا مكان لعامل دائم.

**القرار:** جدول `app.jobs` (مهام + محاولات + `tenant_id` + `run_after`) هو مصدر الحقيقة. `pg_cron` كل دقيقة ينادي دالة SQL تأخذ دفعة بـ`FOR UPDATE SKIP LOCKED` وتستدعي Edge Function عبر `pg_net`، والمهمة تُعلَّم `done` أو تُعاد بتراجع أسّي. كل استدعاء يعالج دفعة صغيرة تنتهي داخل حدود 2 ثانية CPU.

**البدائل:** pg-boss + خادم دائم (يلغي ميزة «بلا خادم»)؛ Supabase Cron وحده بلا جدول مهام (لا إعادة محاولة ولا تتبع)؛ مشغّلات قاعدة (لا تصلح لاستدعاء HTTP طويل).

**النتائج:** (+) صفر تكلفة وصفر خدمات إضافية، والمهمة ذرّية مع معاملة العمل. (−) الجدولة تعمل على نفس الـNano المشترك مع الـAPI، ودقة الجدولة دقيقة واحدة، والمهام الطويلة تحتاج تقسيمًا صريحًا.

**المخاطر:** مهمة تتجاوز حدّها تبقى معلّقة → تخفيف: `attempts` و`locked_at` و`run_after` مع تنبيه عند مهام معلّقة > 15 دقيقة.
**المراجعة:** عند تجاوز 50 ألف مهمة/يوم.

## ADR-024 — التحديث اللحظي عبر Supabase Realtime بقنوات خاصة

**السياق:** لا يمكن فتح WebSocket داخل Edge Function. البديل الأول كان SSE بدفق 120 ثانية: تأخير 3 ثوان، و79,200 استدعاء شهريًا لمخزن واحد. وفي مخزن أدوية، محطتان تصرفان من نفس التشغيلة تحتاجان رؤية الرصيد **قبل** البيع التالي لا بعده.

**القرار:** مشغّل في القاعدة يستدعي `realtime.send(payload, event, 'tenant:<uuid>', private => true)` عند كل حدث عمل. الحمولة **حدث فقط**: نوع + معرّف + نسخة — بلا كميات ولا أسعار ولا بيانات مريض. الواجهة تستقبل الحدث ثم تجلب الحقيقة من `/api` عبر RLS. الاشتراك عبر Supabase Realtime بقناة خاصة، وتوكن ES256 قصير (60 دقيقة) بحمولة `sub`, `role: authenticated`, `tenant_id`, `scope: realtime`؛ مفتاحنا العام مُستورد في المشروع فيتحقق Realtime من توقيعنا بلا Supabase Auth. سياسة `SELECT` واحدة على `realtime.messages` تقارن `realtime.topic()` بـ`tenant_id` من التوكن، و**لا سياسة `INSERT`** (العملاء لا ينشرون).

**البدائل:** SSE (تأخير 3s + 79 ألف استدعاء)؛ استطلاع (432 ألف استدعاء)؛ WebSocket على Cloudflare Durable Objects (خدمة ومنطق إضافيان)؛ Postgres Changes CDC (يرسل صفوفًا كاملة ⇒ بيانات تمر عبر Realtime، مرفوض).

**النتائج:** (+) فوري <300ms. (+) **صفر استدعاءات دالة**، فالسعة ترتفع من 3 إلى 4–5 مخازن. (+) استعادة الرسائل الفائتة عبر Replay. (−) مسار ثانٍ إلى المتصفح يجب تأمينه، واعتماد على ميزة Realtime Authorization، وانقطاع التوكن يقطع القناة كل ساعة.

**التكلفة:** صفر ضمن 2 مليون رسالة و200 اتصال (استهلاكنا ~180 ألفًا و15–40 اتصالًا).
**المخاطر:** انقطاع WebSocket في شبكة المخزن → SSE احتياطي؛ استيراد المفتاح يجعل توكناته مقبولة في PostgREST → `anon`/`authenticated` بلا صلاحيات على `public`.
**المراجعة:** عند 1.4 مليون رسالة أو 150 اتصالًا متزامنًا.

## ADR-025 — حساب واحد = مخزن واحد

**السياق:** طلب المالك قاعدة إلزامية: كل حساب مخزن يملك مخزنًا واحدًا فقط، ولا يستطيع إنشاء مخزن ثانٍ أو فرع أو مستودع إضافي، ولا ربط حسابه بأكثر من مخزن. هذا يتعارض مع ADR-003 الذي سمح بـ`tenant → branches → warehouses`. القاعدة ليست تفضيلًا في الواجهة: لو بقيت في الـGuard فقط، فأي مسار إداري أو خطأ برمجي أو استعلام مباشر يستطيع كسرها، وتفسد التقارير والترخيص وعزل البيانات.

**القرار:** المخزن **1:1** مع الحساب، مثبتًا في القاعدة:

1. `warehouses.tenant_id` يحمل `CONSTRAINT uq_one_warehouse_per_tenant UNIQUE (tenant_id)` — أي إدراج ثانٍ يفشل بـ`23505`، ولو جاء من `psql`.
2. `tenant_memberships.warehouse_id NOT NULL` مع FK مركّب `(tenant_id, warehouse_id) → warehouses(tenant_id, id)`؛ فالعضوية لا تستطيع الإشارة إلى مخزن حساب آخر (`23503`). يُملأ تلقائيًا بـtrigger من مخزن الحساب؛ ولا يُقبل من العميل.
3. حُذف جدول `branches` وكل `branch_id` (في `user_roles`، `user_permission_overrides`، والكيانات الأخرى)، وحُذفت `stock_transfers`/`stock_transfer_items` ونوعا الحركة `transfer_in`/`transfer_out`.
4. الـAPI: لا `POST /warehouses` ولا `/branches` ولا `/stock/transfers`. الموجود `GET /warehouse` و`PATCH /warehouse` (الاسم/العنوان/الترخيص). `warehouse_id` لا يظهر في أي Request Body أو Query أو Path، ويُشتق من العضوية.
5. مسؤول المنصة ينشئ **حسابًا** في معاملة واحدة تُنشئ مخزنه الوحيد وعضوية المالك؛ لا يملك أي مسار يضيف مخزنًا لحساب قائم، ولا يمكنه تغيير القاعدة.
6. الواجهة تعرض بيانات مخزن الحساب فقط، ولا تعرض زر «إضافة مخزن» — لأن المسار غير موجود أصلًا، لا لأنه مخفي.

**البدائل:** (أ) إبقاء التعدد وفرض الحد في الـGuard — مرفوض: قابل للتجاوز من أي مسار جديد. (ب) حد في الخطة (`max_warehouses`) — مرفوض: يجعل القاعدة قابلة للتفاوض التجاري ويكسر التزام المالك. (ج) قاعدة لكل مخزن — مرفوض: تكلفة وتشغيل. (د) إخفاء الزر فقط — مرفوض صراحةً بطلب المالك.

**النتائج:** (+) استحالة المخزن الثاني بنيويًا. (+) `warehouse_id` مشتق لا مُدخل، فيسقط هجوم تمريره. (+) مخطط أبسط: 39 جدولًا بدل 42، واستعلامات بلا تمييز نطاق فرعي. (−) لا دعم فروع لاحقًا بلا ADR جديد وترحيل. (−) من يحتاج مخزنين يفتح حسابين (بضريبة/ترخيص منفصلين) — قرار تجاري للمالك.

**التكلفة:** صفر (حذف جداول ومسارات، لا إضافة بنية).
**المخاطر:** حسابان لنفس الصيدلية يظهران ككيانين → تخفيف: تنبيه في لوحة المنصة عند تشابه الاسم/الترخيص، لا منع آلي. حذف مخزن الحساب → لا مسار حذف؛ الإغلاق يمر بدورة حياة الحساب.
**المراجعة:** عند طلب مؤسسي صريح بفروع؛ يُفتح ADR جديد ولا يُعدَّل هذا.

**التحقق الفعلي (2026-11-08):** نُفِّذ الـDDL كاملًا على PostgreSQL 17 (PGlite): 39 جدولًا، 38 بـ`FORCE RLS`، 44 سياسة، 0 كتلة فاشلة من 41، و**19/19 اختبار PASS** — منها `T19` (مخزن ثانٍ ⇒ `23505`) و`T20` (عضوية بمخزن آخر ⇒ `23503`).

## ADR-026 — بدء نظيف: لا ترحيل بيانات من النظام القديم

**السياق:** النظام الحالي يعمل وبه بيانات تاريخية (أصناف، تشغيلات، أرصدة، فواتير) في قاعدة Supabase قائمة. الافتراض السابق كان ترحيلها بسكربتات تحويل ومطابقة. المالك قرر صراحةً: **لا ترحيل بيانات**. الترحيل يعني تحويلًا آليًا للصفوف، ومطابقة أعداد ومجاميع، ونافذة تجميد، ومخاطر خلط أرصدة — وكلها كلفة وحمل بلا حاجة إذا كان بالإمكان البدء بجرد فعلي.

**القرار:** لا يُنقل أي صف من النظام القديم إلى الجديد، ولا يُكتب سكربت استخراج/تحويل/تحميل. الانتقال:

1. تجميد الإدخال في النظام القديم في موعد معلن.
2. إنشاء الحساب الجديد ومخزنه الوحيد (ADR-025) والمستخدمين من جديد بكلمات مرور Argon2id وMFA.
3. **جرد افتتاحي فعلي موقّع** يُدخل كحركات `opening` موثقة لكل صنف/تشغيلة — إدخال بشري، لا تحميل آلي.
4. التشغيل الفعلي، وفحص `verify_ledger_consistency = 0` قبل أول بيع.
5. النظام القديم يبقى للقراءة والأرشفة؛ تصديره الكامل يُخزَّن للرجوع إليه، ولا يُحمَّل.

**البدائل:** (أ) ترحيل كامل آلي — مرفوض بقرار المالك. (ب) ترحيل الأصناف فقط بلا أرصدة — مرفوض: يخلق كتالوجًا نصف مهاجر ويوهم بأن الأرصدة منقولة. (ج) تشغيل متوازٍ طويل — مرفوض: يضاعف الإدخال ويخلق مصدرَي حقيقة.

**النتائج:** (+) لا مخاطر مطابقة ولا نوافذ تجميد طويلة. (+) JWT/Argon2id من أول يوم بلا GoTrue. (+) دفتر يبدأ من نقطة موثقة. (−) إدخال يدوي للجرد الافتتاحي (مقصود). (−) لا تاريخ مبيعات/مشتريات في النظام الجديد قبل تاريخ البدء — التقارير التاريخية تُقرأ من أرشيف القديم.

**التكلفة:** صفر تقنيًا؛ كلفة تشغيلية = جرد افتتاحي.
**المخاطر:** خطأ في العدّ الافتتاحي → تخفيف: عدّ مزدوج، توقيع المالك، وفحص اتساق إلزامي قبل أول بيع. الاعتماد على أرشيف قديم للتقارير → تصدير كامل موثّق ومحفوظ.
**المراجعة:** عند طلب المالك ترحيل تاريخ محدد لاحقًا؛ يُفتح ADR جديد بمتطلبات مطابقة صريحة.
