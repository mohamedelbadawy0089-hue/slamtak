# 23 — عقد OpenAPI v1

> **الحالة:** مكتمل ومُتحقَّق آليًا — بند Gate B الثاني.
> **الملف الملزم:** [`api/openapi.yaml`](api/openapi.yaml) (OpenAPI 3.1.0).
> **المرجع المعماري:** `10-api-architecture.md` — هذه الوثيقة تُجسّد قراراته في عقد قابل للتنفيذ، ولا تعارضه.

## 1. لماذا ملف عقد وليس وصفًا نصيًا

في المراحل السابقة كان كتالوج المسارات في `10` جدولًا وصفيًا. الجدول الوصفي لا يمنع ثلاثة أخطاء شائعة:

1. مسار منفذ بلا عقد → عميل يخمّن شكل الاستجابة.
2. رمز خطأ يظهر في الكود ولا يوجد في التوثيق.
3. عقد يُعلن `If-Match` ثم لا يفرضه الخادم.

لذلك صار العقد **ملفًا آليًا** يُفحص في CI، ويُولَّد منه نوع TypeScript للواجهة والاختبارات، وأي انحراف بين الكود والعقد يُفشل البناء.

| مواصفة | OpenAPI 3.1.0 (JSON Schema 2020-12) |
| المسارات | 65 |
| العمليات | 89 |

| الاستجابات المشتركة | 31 |

## 3. القواعد المفروضة في العقد نفسه

### 3.1 لا تفويض من جسم الطلب

`LoginRequest` يقبل `tenantSlug` **اختياريًا** لتحديد الحساب عند تعدد العضويات، ووصفه في العقد ينص صراحة أنه «لا يُستخدم للتفويض». لا يوجد أي مخطط يحتوي `tenantId` أو `warehouseId` قابلًا للكتابة:

```yaml
# لا يوجد في أي Request Body:
#   tenantId: ...      ← مرفوض تصميميًا
#   warehouseId: ...   ← مرفوض؛ 400 WAREHOUSE_CONTEXT_NOT_ACCEPTED
```

`warehouse_id` يُشتق من `tenant_memberships.warehouse_id` المرتبط بمخزن الحساب الوحيد، و`RLS` يفرض `tenant_id` على مستوى القاعدة (`22`). لا مسار لإنشاء مخزن ثانٍ: `POST /warehouses` و`/branches` غير موجودين، والقاعدة ترفض الإدراج المباشر بـ`23505` (ADR-025).

### 3.2 التسعير على الخادم

`SalesInvoiceInput` لا يحتوي سعرًا إطلاقًا — الحقول هي `medicineId`, `qty`, `discountPct` فقط. السعر يعود في `SalesInvoiceLine.unitPrice` بوصفه «محسوب على الخادم من قائمة الأسعار». بهذا يستحيل على العميل تثبيت سعر.

### 3.3 تخصيص FEFO ظاهر في العقد

`SalesInvoiceLine.allocations` ليست تفصيلًا داخليًا؛ هي جزء من العقد، لأن المستخدم النهائي يجب أن يرى من أي تشغيلة صُرف الدواء (متطلب دستوري في مخازن الأدوية: التتبع والتسجيل). الحقل إلزامي في الاستجابة.

### 3.4 لا تعديل رصيد مباشر

`AdjustmentRequest` يفرض `reason` (5–500 حرف) بوصفه إلزاميًا، والوصف ينص: «إلزامي دائمًا — لا تسوية بلا سبب موثق». لا يوجد مسار `PATCH /stock` أو `PUT /stock/batches/{id}`.

### 3.5 الأخطاء موحدة

كل استجابة خطأ من نوع `application/problem+json` ومخططها `Problem` مع `code` ثابت و`requestId`. التوزيع الفعلي في العقد:

| الرمز | عدد العمليات التي توثّقه |
|---|---|
| 200 | 55 |
| 201 | 29 |
| 202 | 2 |
| 204 | 6 |
| 401 | 35 |
| 403 | 21 |
| 404 | 10 |
| 409 | 27 |
| 422 | 35 |
| 423 | 5 |
| 428 | 3 |
| 429 | 4 |
| 503 | 1 |

**قاعدة مطبقة آليًا:** كل عملية محمية توثّق `401`؛ العمليات العامة الوحيدة هي `login`, `mfa/verify`, `platform/health` (و`refresh` يعتمد كوكي التجديد).

### 3.6 الاستجابات العامة (`Problem`) تحمل أمثلة حقيقية

مثال `INSUFFICIENT_STOCK` في العقد يحمل `errors[0].field = lines[2].qty` — نفس الشكل الذي يُعيده `GlobalExceptionFilter` في `07`. لا فرق بين ما يوثّقه العقد وما يراه العميل.

## 4. ما لا يغطيه العقد (بصراحة)

| البند | السبب | أين يُعالج |
|---|---|---|
| Webhooks الصادرة | عقد منفصل (المستهلك نحن) | `10` §12 — يحتاج `webhooks.yaml` مستقلًا عند تنفيذ التكاملات |
| الرفع متعدد الأجزاء للمرفقات | يستخدم `multipart/form-data` مع فحص فيروسات غير متزامن | `13` §3.2 |
| الموافقات متعددة الخطوات | حالة سير عمل داخلية، لا عقد شبكي | `12` — تُنمذج كـ `approval_requests` |
| التقارير المخصصة | صفوف مرنة `ReportRow` | `packages/contracts/reports` — مخطط لكل تقرير لاحقًا |
| التصدير الثنائي (xlsx) | الملف يُسلَّم عبر رابط موقّع لا عبر JSON | `10` §11 |

**هذا التصريح مقصود:** عقد يدّعي تغطية كل شيء أسوأ من عقد يحدد حدوده.

## 5. نتائج التحقق الفعلي

شُغّل فاحص OpenAPI حقيقي (Redocly CLI 1.34.24) على الملف:

```bash
npx @redocly/cli lint docs/architecture/api/openapi.yaml
```

| البند | النتيجة |
|---|---|
| صحة البنية (OpenAPI 3.1) | ✅ valid |
| أخطاء | **0** |
| تحذيرات | **0** |
| مراجع `$ref` مفقودة | 0 |
| `operationId` مكرر | 0 (فُحص برمجيًا: 89 قيمة فريدة) |
| عملية بلا استجابة خطأ | 0 |
| `securitySchemes` غير مستخدمة | 0 |

كما فُحص برمجيًا عبر `yaml.safe_load` + تحليل كامل للشجرة:
- 89 عملية، كل واحدة لها `operationId` فريد و`tags` و`responses`.
- العمليات التي تعيد تعريف الأمان هي فقط: `login`, `verifyMfa`, `refresh`, `platformHealth`.
- `issueRealtimeToken` (`POST /auth/realtime-token`) هو المسار الوحيد الذي يصدر توكنًا **بصلاحية اشتراك فقط** (`scope: realtime`)؛ لا يفتح بيانات ولا يصلح لبقية الـAPI (`28` §7.1).

## 6. كيف يُستخدم العقد في CI

```yaml
# .github/workflows/contract.yml (مقتطف مخطَّط — لم يُنفَّذ بعد)
- run: npx @redocly/cli lint docs/architecture/api/openapi.yaml
- run: npx openapi-typescript docs/architecture/api/openapi.yaml -o packages/contracts/src/api.d.ts
- run: npx vitest run packages/contracts -- --check-drift   # يفشل إذا تغيّر المولَّد
```

| البوابة | الشرط |
|---|---|
| G1 | `lint` بلا أخطاء |
| G2 | المولَّد في `packages/contracts` مطابق للملف (لا انحراف) |
| G3 | كل `operationId` له اختبار تكامل واحد على الأقل (`16`) |
| G4 | كل مسار كتابي مغطّى باختبار صلاحية (Deny by default) |

**G3 وG4 هما ما يمنع «عقدًا جميلًا بلا تنفيذ»** — العقد موجود، والاختبارات تأتي مع Phase 1.

## 7. الفرق بين العقد والتوثيق التسويقي

| سؤال | الجواب في هذا العقد |
|---|---|
| هل يمكن للعميل تحديد المخزن؟ | لا — لا حقل، والمعرّف من العضوية |
| هل يمكن إنشاء مخزن ثانٍ للحساب؟ | لا — لا مسار، و`UNIQUE (tenant_id)` يرفض `23505` (ADR-025) |
| هل يمكنه تحديد السعر؟ | لا — الحقل غير موجود في المدخل |
| هل يمكنه تعديل رصيد؟ | لا — نجاح التسوية يتطلب `reason` + `X-Step-Up` |
| ماذا يحدث عند إعادة إرسال الطلب؟ | نفس الاستجابة (`Idempotency-Key`، 24 ساعة) |
| ماذا يرى عند الوصول لمورد مخزن آخر؟ | `404 RESOURCE_NOT_FOUND` لا `403` |
| هل يوجد مسار بلا 401 موثّق؟ | 3 فقط وكلها عامة عن قصد |
