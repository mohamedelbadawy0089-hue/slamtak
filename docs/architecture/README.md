# معمارية نظام إدارة مخازن الأدوية — Slamtak WMS

> **حالة التسليم:** مسودة للمراجعة والاعتماد (Design Review Draft v1.0) — **لا كود تنفيذي في هذه المرحلة**.
> **النطاق:** مخزن أدوية واحد الآن، قابل للتحول إلى منصة SaaS متعددة المخازن دون إعادة بناء.
> **اللغة:** العربية للوثائق، الإنجليزية للمصطلحات المعمارية وأسماء الجداول والواجهات.
> **غير تقني؟** ابدأ بـ [الملخص التنفيذي](EXECUTIVE-SUMMARY.md) — صفحة واحدة: ماذا ستشتري، وبكم، ومتى، وما نحتاجه منك.
> **قيد حاكم (2026-11-06):** التكلفة في التطوير والتجربة والتشغيل الأولي = **صفر**، بلا بطاقة ولا فوترة تلقائية. [`27`](27-free-tier-architecture.md) هو المرجع الحاكم لكل قرار سحابي، وأي ذكر لتكلفة شهرية أو Redis/BullMQ أو VPS في الوثائق `00`–`20` مُستبدَل به.

## 3. القرارات الحاكمة (ملخص تنفيذي)

هذه عشرة قرارات تحكم كل ما بعدها؛ تفاصيلها وأسبابها وبدائلها في `20-adr.md`.

| # | القرار | الأثر |
|---|---|---|
| 1 | **Modular Monolith** داخل بوابة واحدة (Edge Functions) بحدود وحدات صريحة — لا Microservices | سرعة تسليم، تكلفة منخفضة، قابلية فصل لاحقة |
| 2 | **قاعدة بيانات مشتركة + عزل منطقي** بـ `tenant_id` و RLS على **كل** جدول أعمال | عزل مثبت على مستوى القاعدة، لا يعتمد على كود التطبيق |
| 3 | **حساب واحد = مخزن واحد** (ADR-025): `tenants` و`warehouses` بعلاقة 1:1 يفرضها `UNIQUE (tenant_id)` — لا فروع ولا مخزن ثانٍ | يمنع خلط الحساب بالموقع، ويُغلق إمكانية توسيع النطاق بمخزن إضافي |
| 4 | **Edge Functions هي بوابة الوصول الوحيدة للبيانات**؛ `REVOKE` يلغي وصول المتصفح لـ PostgREST | منطق الأعمال والأسعار والمخزون على الخادم |
| 5 | **مصادقة ذاتية في البوابة** (Argon2id + JWT ES256 + Refresh Rotation) بدل Supabase Auth | تحكم كامل في MFA والتحقق الثاني والسياسات |
| 6 | **PostgreSQL مُدار** (Supabase/Neon) + **Drizzle ORM** + معاملات صريحة | تحكم دقيق في `SET LOCAL` و RLS |
| 7 | **أصل واحد عام** (`app.`) مع توجيه `/api` داخليًا للـ API | يلغي مشاكل CORS و CSRF وكوكيز الطرف الثالث |
| 8 | **كل تغيير في المخزون = حركة موثقة (Ledger)**؛ لا تعديل أرصدة مباشر | قابلية التتبع والمراجعة والتسوية |
| 9 | **FEFO إلزامي** للصرف مع حجب التشغيلات المنتهية/المحجوزة على مستوى القاعدة والخادم | مطابقة تنظيمية وسلامة دوائية |
| 10 | **Event-Driven داخلي** عبر Outbox + `app.jobs`/`pg_cron`، وليس رسائل مباشرة بين الوحدات | اتساق المعاملات + قابلية إعادة المحاولة |

## 4. المبادئ المعمارية العشرة

1. **Security-First:** كل endpoint يُفترض أنه مكشوف حتى يُثبت العكس (Deny by default).
2. **Tenant-First:** لا استعلام بدون سياق مخزن مُشتق من الخادم.
3. **API-First:** العقد (OpenAPI + Zod) يُكتب قبل الواجهة، والواجهة تُستهلك من عقد مولّد.
4. **Modularity بحدود:** كل وحدة تملك جداولها ومنطقها، وتتواصل مع غيرها عبر واجهة معلنة أو حدث.
5. **Data Integrity in DB:** القيود والمفاتيح الخارجية والـ RLS في القاعدة، وليست "عُرفًا" في الكود.
6. **Auditability:** كل عملية حساسة لها أثر لا يُحذف ولا يُعدَّل.
7. **Idempotency:** كل عملية مالية أو مخزنية قابلة لإعادة الإرسال بأمان.
8. **Observability:** كل طلب له `requestId`، وكل وحدة تُصدر مقاييس وسجلات منظمة.
9. **Cost-Awareness:** لا نضيف مكوّنًا (Redis، Queue، Replica، Microservice) قبل بلوغ عتبة موثقة في `17`.
10. **Reversibility:** كل قرار قابل للتراجع بخطة هجرة مكتوبة (Expand → Migrate → Contract).

## 5. بوابات المراجعة والاعتماد (Review Gates)

**قراءة الحالة:** `[x]` = المخرج موجود ومُتحقَّق منه بقدر ما تسمح به مرحلة التصميم. `[ ]` = إما لم يُنفَّذ (بوابات ما بعد الكود) أو ينتظر قرارك. لا يوجد بند واحد بين البوابات الثلاث بلا مرجع يثبته.

### Gate A — اعتماد المعمارية (هذه المرحلة)
- [x] تصور واضح لكل الطبقات العشر (→ `01`, `03`).
- [x] دورة الاتصال واجهة → خادم → قاعدة بيانات موثقة خطوة بخطوة (→ `01` §6, `10` §7).
- [x] التقنيات وإصداراتها الخط الأساسي مذكورة مع سبب كل تقنية (→ `05`).
- [x] علاقات قاعدة البيانات والقيود والمفاتيح محددة (→ `08`, `09`؛ مُنفَّذة فعليًا في `21`: 39 جدولًا + 4 في `platform`).
- [x] آلية عزل المخازن مثبتة على مستوى القاعدة (→ `11`؛ مُثبتة بالتنفيذ في `22`: `T1`–`T5`).
- [x] آلية الصلاحيات محددة (RBAC + Scope) (→ `12`؛ أربعة أدوار قاعدة بأقل امتياز (المالك + التطبيق + المنصة + التشغيل)، مُختبرة في `T5`/`T15`–`T17`).
- [x] طريقة النشر والتحديث والتراجع محددة (→ `15`؛ والتراجع المُلزَم في `26` §5.2).
- [x] طريقة الاختبار والمراقبة محددة (→ `14`, `16`؛ والتنبيهات في `26` §4).

- [x] كل قرار معماري له سبب وبدائل وتكلفة ومخاطر (→ `20`: ADR-001…ADR-018).

**حالة Gate A:** كل بند له مخرج قابل للفحص، وبعضها مُثبت بالتنفيذ لا بالوصف؛ **التوقيع وحده متبقٍّ**.

### Gate B — اعتماد المخطط التفصيلي (قبل Phase 1)
- [ ] DDL مرجعي كامل للجداول الأساسية + سياسات RLS + اختبار عزل ناجح على بيئة تجريبية. → **مُهيّأ في `21` و`22`** (17 اختبار عزل وسلامة ناجح فعليًا: `T1`–`T17`)، ينتظر توقيعك.
- [ ] عقد OpenAPI v1 معتمد (مسارات، أخطاء، ترقيم صفحات، Idempotency). → **مُهيّأ في `23`** (65 مسارًا، 89 عملية، فحص آلي: 0 خطأ و0 تحذير)، ينتظر توقيعك.
- [ ] مخططات تدفق: بيع، استلام، تحويل، جرد، مرتجع. → **مُهيّأ في `24`** (5 تدفقات + آلة حالات)، ينتظر توقيعك.
- [ ] نموذج التهديد (STRIDE) معتمد من مسؤول الأمن. → **مُهيّأ في `25`** (A1–A26، 4 حالات مُختبرة تنفيذيًا)، ينتظر اعتماد مسؤول الأمن.

### Gate C — اعتماد جاهزية الإنتاج (قبل أول عميل)
- [ ] استعادة نسخة احتياطية مُختبرة (Restore Drill) بنجاح. → إجراء ومعايير الفشل في `26` §1؛ **التنفيذ لم يحدث**.
- [ ] اختبار عزل بين مخزنين آليًا في CI (يفشل البناء عند أي تسريب). → مواصفة البوابة في `26` §2؛ لا مستودع كود بعد.

## 6. قرارات مطلوبة من مالك المنتج (قبل Phase 1)

اثنا عشر قرارًا لا توقف التصميم، لكنها تغيّر التفاصيل وتحتاج حسمًا. العشرة الأولى لها افتراض مؤقت مُطبَّق فعلًا في الوثيقة المعنية — أي أن تأخير الحسم لا يوقف العمل — والحادي عشر (الاستضافة) والثاني عشر (التحديث اللحظي) **حُسما بتاريخ 2026-11-06**:

| # | السؤال | الافتراض المؤقت في هذه الوثائق |
|---|---|---|
| 1 | هل تُرحَّل بيانات المخزن الحالي من مشروع Supabase القائم أم نبدأ نظيفًا؟ | **بدء نظيف — لا ترحيل بيانات** ([`20`](20-adr.md) ADR-026): جرد افتتاحي موقّع يُدخل كحركات `opening` |
| 2 | الميزانية الشهرية المستهدفة للبنية التحتية؟ | **صفر** حتى حدود الخطط المجانية (لا بطاقة ولا فوترة تلقائية)، والترقية قرار تعاقدي لاحق ([`27`](27-free-tier-architecture.md)) |
| 3 | هل الفاتورة الإلكترونية (ETA) مطلوبة في المرحلة الأولى؟ | تُصمَّم الآن كوحدة تكامل، وتُنفَّذ في Phase 5 |
| 4 | عدد المستخدمين المتزامنين المتوقع للمخزن الأول؟ | 25–40 متزامنًا، 200 مستخدم إجمالي |
| 5 | هل يلزم دعم فروع متعددة للمخزن الأول؟ | **لا — قرار المالك:** حساب واحد = مخزن واحد، بقيد قاعدة بيانات ([`20`](20-adr.md) ADR-025) |
| 6 | من يُصدر شهادة الاعتماد الأمني النهائي؟ | مراجعة داخلية + فحص آلي (ZAP/Trivy) في هذه المرحلة |
| 7 | هل `allocations` (تفصيل تخصيص FEFO لكل سطر بيع) إلزامية في الاستجابة؟ | **نعم** — شفافية التتبع أولى من حجم الاستجابة ([`23`](23-openapi-contract.md)) |
| 8 | في التحويل بين المخازن: خصم عند الإرسال أم عند الاستلام؟ | **لا تحويلات:** لا مخزن ثانٍ لنقل إليه؛ أُلغيت الجداول والمسارات ([`20`](20-adr.md) ADR-025) |
| 9 | هل يُنفَّذ اختبار اختراق خارجي قبل أول عميل مدفوع (R1)؟ | **نعم**، وميزانيته تُحسم في Phase 1 لا في التصميم ([`25`](25-threat-model.md) — R1) |
| 10 | من المناوب (On-call) قبل الإطلاق، وما قناة الحوادث؟ | مناوب واحد من فريق الـ backend، وقناة حادث واحدة موثّقة ([`26`](26-production-readiness.md) §5) |
| 11 | أين يُشغَّل الـ API في الإنتاج بلا تكلفة؟ | **حُسم مرتين:** Edge Functions هي البوابة ([`28`](28-supabase-edge-runtime.md))؛ Oracle/Google بقيت احتياطًا اختياريًا بلا بطاقة ([`27`](27-free-tier-architecture.md) §10.1) |
| 12 | كيف يرى المستخدم تحديث الآخرين: فوري أم عند التحديث؟ | **فوري** عبر Supabase Realtime بقناة خاصة، والحمولة حدث بلا بيانات ([`28`](28-supabase-edge-runtime.md) §7.1 · ADR-024) |

## 7. ما لا يشمله هذا التسليم

- لا كود تطبيقي، ولا ملفات هجرة فعلية (DDL مرجعي داخل الوثائق فقط).
- لا إعداد بنية تحتية سحابية ولا شراء نطاق/شهادات.
- لا تكامل فعلي مع جهات خارجية (ETA، بوابات دفع، SMS) — التصميم والعقد فقط.
- لا اختبار حمل حقيقي — الأهداف والأدوات محددة، والأرقام تُقاس في Phase 1.

## 8. اصطلاحات الوثائق

- **Tenant**: حساب مخزن أدوية مستقل (وحدة العزل والفواتير).
- **Warehouse**: المخزن الوحيد للحساب (1:1)؛ يحمل الاسم والعنوان ورقم الترخيص. لا يوجد مستوى «فرع».
- **Batch/تشغيلة**: دفعة دواء برقم تشغيلة وتاريخ انتهاء.
- **FEFO**: First-Expiry-First-Out — الصرف حسب الأقرب انتهاءً.
- **RLS**: Row Level Security في PostgreSQL.
- **Outbox**: جدول أحداث يُكتب في نفس معاملة العمل ثم يُنشر لاحقًا.
- المخططات: Mermaid (تُعرض تلقائيًا في GitHub/VS Code). مخططات C4 مرسومة بـ `flowchart` لضمان العرض في كل العارضات.
